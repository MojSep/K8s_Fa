🏗️ معماری توصیه‌شده (Layered Best Practice)
text

┌─────────────────────────────────────────────────────────┐
│  Layer 4: Application Workloads                         │
│  → GitOps (ArgoCD / Flux) + Helm / Kustomize            │
│  → manifests در Git، apply خودکار                       │
├─────────────────────────────────────────────────────────┤
│  Layer 3: Cluster Add-ons                               │
│  → Terraform (helm provider) یا ArgoCD                  │
│  → ingress-nginx, cert-manager, monitoring              │
├─────────────────────────────────────────────────────────┤
│  Layer 2: Kubernetes Cluster                            │
│  → Terraform (EKS/GKE/AKS module)                       │
│  → VPC, Node Groups, IAM, RBAC اولیه                    │
├─────────────────────────────────────────────────────────┤
│  Layer 1: Cloud Infrastructure                          │
│  → Terraform / Pulumi / Crossplane                      │
│  → VPC, Subnets, Load Balancers, Databases              │
└─────────────────────────────────────────────────────────┘

        Python → فقط برای Automation سفارشی و Operators
        kubectl → فقط برای Debugging و Manual Ops

❌ ضدالگوها (Anti-patterns)
hcl

# ❌ هرگز workload اپلیکیشن را با Terraform مدیریت نکن
resource "kubernetes_deployment" "api" {
  metadata { name = "api" }
  spec {
    replicas = 3
    # این کار state را شکننده می‌کند
  }
}

🔧 دلایل:

    State سنگین — با هر تغییر deployment باید terraform apply بزنی

    تعارض با GitOps — ArgoCD و Terraform هر دو می‌خواهند مالک باشند (Conflict)

    Rollback سخت — kubectl rollout undo سریع‌تر از terraform apply قبلی است

    CI/CD کندتر — Terraform plan/apply برای هر deploy، کند است

    فقدان progressive delivery — Canary، Blue/Green با ArgoCD راحت‌تر است

⚠️ استثنا: در تیم‌های کوچک که زیرساخت و اپ یکی است، kubernetes_* provider قابل قبول است ولی برای Scale-Up مهاجرت به GitOps ضروری می‌شود.
🟢 2. GitOps (کوبectl + YAML) — استاندارد طلایی Workloads
✅ Best Practice معماری
text

GitHub Repo

مثال Kustomize
yaml

# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
images:
  - name: api
    newTag: v1.2.3

# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - target:
      kind: Deployment
      name: api
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 10

ArgoCD Application
yaml

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/org/k8s-manifests
    path: apps/api/overlays/prod
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true    # ← drift خودکار اصلاح می‌شود

✅ چرا این بهترین است؟
ویژگی	مزیت
Single Source of Truth	Git = وضعیت واقعی
Audit Trail	هر تغییر PR دارد و کامیت شده
Rollback سریع	git revert → ArgoCD خودکار sync
Drift Detection	selfHeal: true انحراف را اصلاح می‌کند
Multi-env	overlay‌های Kustomize/Helm values
تیم-friendly	dev و ops روی یک repo کار می‌کنند
Security	ArgoCD داخل کلاستر — دسترسی مستقیم به prod لازم نیست
🛠️ kubectl — فقط برای این موارد

# ✅ Manual scaling اضطراری

📋 جدول تصمیم‌گیری
کار	ابزار توصیه‌شده
ساخت EKS/GKE/AKS	✅ Terraform
VPC, IAM, S3, RDS	✅ Terraform
نصب Cert-Manager / Ingress-NGINX	✅ Terraform (helm) یا ArgoCD
Deployment یک اپ	✅ ArgoCD + Kustomize/Helm
ConfigMap / Secret	✅ ArgoCD + Sealed Secrets / External Secrets
تغییر تعداد replicas	✅ Git commit → ArgoCD sync
Canary / Blue-Green	✅ Argo Rollouts (GitOps-compatible)
دیباگ یک پاد در حال کرش	✅ kubectl
اضافه کردن node اضطراری	✅ Terraform
Custom Resource + منطق پیچیده	✅ Python (kopf)
Preview Environment خودکار	✅ Python + ArgoCD ApplicationSet
Testing و Chaos	✅ Python (chaos-mesh, kube-monkey)
🎯 قانون طلایی (Golden Rules)
1️⃣ Declarative over Imperative

    هر چیزی که می‌خواهی بماند، باید Declarative باشد.
    kubectl set/edit = فقط برای مواردی که می‌خواهی موقت باشد.

2️⃣ Git as Single Source of Truth

    اگر در Git نیست، وجود ندارد.
    Python و kubectl اگر تغییر می‌دهند، باید خودشان را از Git همگام کنند (یا ArgoCD آن را اصلاح کند).

3️⃣ Layered Ownership
text

Terraform  →  زیرساخت و کلاستر (state دارد)
ArgoCD     →  منابع داخل کلاستر (Git دارد)
Python     →  منطق پیچیده که دو تای بالا نمی‌توانند (نادر)
kubectl    →  مشاهده و دیباگ (بدون تغییر پایدار)

4️⃣ هرگز دو ابزار روی یک منبع

    یک منبع K8s نباید هم‌زمان توسط Terraform و ArgoCD مدیریت شود → Conflict و Drift Loop می‌سازد.

5️⃣ اگر Python می‌نویسی، دلیل مستند کن

    در README بنویس: چرا ArgoCD/Terraform کافی نبود؟
    این سوال در Code Review باید جواب داشته باشد.

🧪 سناریوی واقعی — تیم ۵ نفره

قبل از Best Practice (Anti-pattern):
text

DevOps با kubectl deploy می‌کند ❌
Infra با ClickOps در AWS Console ❌
Python script فقط برای اپ deploy (چرا؟) ❌

بعد از Best Practice:
text

Terraform       → VPC, EKS, IAM, RDS, Add-ons
ArgoCD + Helm   → Deployments, Services, Ingress
Sealed Secrets  → Secrets
Python (kopf)   → Operator برای DB provisioning سفارشی
kubectl         → فقط debug

📌 جمع‌بندی یک‌خطی

    Terraform برای ساخت کلاستر، GitOps (ArgoCD) برای اجرای اپ، kubectl برای دیباگ، Python فقط وقتی که هیچ‌کدام جواب ندهند.
