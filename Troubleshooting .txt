۱.۱ — Incident Response Lifecycle
text

Alert / Page
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 1. TRIAGE (۲ دقیقه)                                     │
│   - Severity? (SEV1=prod down, SEV2=degraded, SEV3=warn)│
│   - Scope? (1 pod / 1 node / 1 zone / whole cluster)    │
│   - Impact? (users / revenue / SLA)                     │
│   - Recent changes? (deploy, config, infra)             │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 2. MITIGATE (اولویت!)                                   │
│   - Rollback (اگر deploy بود)                           │
│   - Scale up (اگر resource)                             │
│   - Drain node (اگر infra)                              │
│   - Disable feature flag                                │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 3. DIAGNOSE (بعد از stabilize)                          │
│   - Layer by layer                                      │
│   - Preserve evidence                                   │
│   - Document timeline                                   │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 4. RESOLVE                                              │
│   - Fix root cause                                      │
│   - Verify with smoke test                              │
│   - Update runbook                                      │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 5. POSTMORTEM (24-48h بعد)                              │
│   - Blameless RCA                                       │
│   - Action items                                        │
│   - Prevention                                          │
└─────────────────────────────────────────────────────────┘

۱.۲ — قانون طلایی: "Mitigate First, Diagnose Second"

اشتباه رایج تازه‌کارها: تلاش برای پیدا کردن root cause قبل از متوقف کردن bleeding. در production، اول کاربر را نجات بده، بعد ریشه را پیدا کن.
bash

# ❌ اشتباه:
kubectl logs api-xyz | grep error | head -100  # کاربر همچنان down

# ✅ درست:
kubectl rollout undo deploy/api -n prod        # کاربر برمی‌گردد
# سپس:
kubectl logs api-xyz --previous | grep error   # ریشه

# krew
(
  set -x; cd "$(mktemp -d)" &&
  OS="$(uname | tr '[:upper:]' '[:lower:]')" &&
  ARCH="$(uname -m | sed -e 's/x86_64/amd64/' -e 's/\(arm\)\(64\)\?.*/\1\2/' -e 's/aarch64$/arm64/')" &&
  KREW="krew-${OS}_${ARCH}" &&
  curl -fsSLO "https://github.com/kubernetes-sigs/krew/releases/latest/download/${KREW}.tar.gz" &&
  tar zxvf "${KREW}.tar.gz" &&
  ./"${KREW}" install krew
)

export PATH="${KREW_ROOT:-$HOME/.krew}/bin:$PATH"

# پلاگین‌های ضروری
kubectl krew install stern ctx ns neat tree debug df-pv images cost oomd sick doctor

۳.۲ — Stern — لاگ همه پادهای یک label
bash

# نصب: kubectl krew install stern

# همه پادهای یک deployment:
stern -n prod deploy/api --since 10m

# چند label:
stern -n prod -l app=api,tier=backend --since 5m

# regex روی pod name:
stern -n prod 'api-.*' --since 10m

# همه پادهای یک node:
stern -n prod --field-selector spec.nodeName=worker1

# با output JSON برای parse:
stern -n prod deploy/api -o json | jq 'select(.message | contains("error"))'

# فقط خطاها:
stern -n prod deploy/api --since 1h | grep -iE "error|exception|fail"

T=0min — Alert دریافت شد:
text

[FIRING:High5xxRate] error rate 12% (threshold 1%) for 5m

T+2min — Triage:
bash

# ۱. چه چیزی تغییر کرده؟
kubectl rollout history deploy/api -n prod
# REVISION  CHANGE-CAUSE
# 41        <none>
# 42        <none>

kubectl get deploy api -n prod -o jsonpath='{.status.updatedReplicas}/{.status.replicas}'
# انتظار: اگر 3/5 → rolling update در جریان است

# ۲. لاگ‌های ۵ دقیقه‌ی اخیر:
stern -n prod deploy/api --since 5m | grep -iE "error|5[0-9]{2}"

# خروجی نمونه:
# api-7f8c9-abc api ERROR db connection refused: dial tcp 10.0.1.50:5432
# api-7f8c9-def api ERROR db connection refused

T+4min — Mitigate (اولویت):
bash

# اگر آخرین deploy مشکوک است:
kubectl rollout undo deploy/api -n prod
kubectl rollout status deploy/api -n prod --timeout=5m

# ✅ چک: error rate برمی‌گردد؟
# (از Grafana یا:)
watch -n 5 'kubectl get pods -n prod -l app=api | grep -c Running'

T+10min — Diagnose Root Cause:
bash

# چرا db connection refused؟
kubectl get svc -n prod db
kubectl get endpointslices -n prod -l kubernetes.io/service-name=db
# NAME       ADDRESSES
# db-xyz     []               ← خالی!

# چرا endpoint خالی؟
kubectl get pods -n prod -l app=db
# NAME         READY   STATUS
# db-0         0/1     Running     ← Ready نیست

kubectl describe pod db-0 -n prod | tail -20
# Events:
# Warning  Unhealthy  Readiness probe failed: dial tcp 10.0.1.50:5432: connect: connection refused

T+15min — Fix Root Cause:
bash

# پاد db Ready نیست — چرا؟
kubectl logs db-0 -n prod --tail=50
# ERROR: FATAL: password authentication failed

# چک secret:
kubectl get secret db-credentials -n prod -o jsonpath='{.data.password}' | base64 -d
# newpass123

# چک env pod:
kubectl exec db-0 -- env | grep PASSWORD
# PASSWORD=oldpass456  ← stale!

# علت: secret از ۲ روز پیش تغییر کرده، پادهای قبلی restart نشده‌اند
kubectl rollout restart sts/db -n prod

# ✅ چک:
kubectl get endpointslices -n prod -l kubernetes.io/service-name=db
# ADDRESSES: [10.0.1.50]  ← حالا پر

T+20min — Verify:
bash

# Smoke test:
kubectl run test --rm -it --image=curlimages/curl -n prod -- \

# Grafana → error rate < 1%

🎭 سناریو ۲: "Pod stuck in Pending"

T=0:
bash

kubectl get pods -n prod | grep Pending
# payment-api-xyz   0/1   Pending   0   15m

T+1min — Describe (همیشه اول):
bash

kubectl describe pod payment-api-xyz -n prod | tail -15
# Events:
# Warning  FailedScheduling  default-scheduler  0/5 nodes are available:
#          3 node(s) had untolerated taint {dedicated: payment},
#          1 Insufficient memory,
#          1 node(s) didn't match Pod's node affinity/selector.

T+2min — تحلیل:
bash

# کدام نودها taint دارند؟
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
# NAME      TAINTS
# worker1   [map[effect:NoSchedule key:dedicated value:payment]]
# worker2   [map[effect:NoSchedule key:dedicated value:payment]]
# worker3   <none>
# worker4   <none>
# worker5   <none>

# منابع:
kubectl describe nodes | grep -A3 "Allocated resources"
# worker3: memory requests: 95%
# worker4: memory requests: 60%
# worker5: memory requests: 40%

# affinity pod:
kubectl get pod payment-api-xyz -n prod -o jsonpath='{.spec.affinity}' | jq .
# انتظار: nodeSelector یا affinity به dedicated=payment

T+3min — تشخیص:

پاد به nodeSelector: dedicated=payment نیاز دارد، اما آن نودها فقط taint دارند و نه label. mismatch بین taint و toleration.
bash

# چک label ها:
kubectl get nodes --show-labels | grep dedicated
# worker1: ... dedicated=payment ...
# worker2: ... dedicated=payment ...
# (ظاهراً label هست)

T+4min — Re-check:
bash

# چرا pod روی worker1/2 زمان‌بندی نمی‌شود؟
kubectl describe pod payment-api-xyz -n prod | grep -A5 "Tolerations"
# Tolerations: (none)  ← ❗

# علت: pod toleration ندارد! فقط nodeSelector دارد.
# اما taint روی نودها آن را دفع می‌کند.

T+5min — Fix:
yaml

# deployment.yaml
spec:
  template:
    spec:
      nodeSelector:
        dedicated: payment
      tolerations:              # ← این را اضافه کن
        - key: dedicated
          operator: Equal
          value: payment
          effect: NoSchedule

bash

kubectl apply -f deployment.yaml
kubectl get pods -n prod | grep payment
# payment-api-abc   1/1   Running   ← ✅

🔧 درس: nodeSelector + taint بدون toleration = Pending. label = "من اینجا را دوست دارم"، toleration = "من می‌توانم اینجا باشم".

T+2min — اگر 137 (OOMKilled):
bash

# limits چقدر؟
kubectl get pod worker-xyz -n prod -o jsonpath='{.spec.containers[0].resources}' | jq .
# {
#   "limits": {"memory": "256Mi"},
#   "requests": {"memory": "128Mi"}
# }

# مصرف واقعی:
kubectl top pod worker-xyz -n prod
# NAME          CPU(cores)   MEMORY(bytes)
# worker-xyz    450m         240Mi    ← نزدیک limit

bash

kubectl set resources deploy/worker -n prod \
  --limits=memory=512Mi --requests=memory=256Mi

# ✅ چک:
kubectl get pods -n prod -l app=worker -w
# انتظار: rolling update، همه Running

bash

kubectl exec worker-xyz -- cat /sys/fs/cgroup/memory.current

# heap dump (اگر Node.js):
kubectl exec worker-xyz -- node --inspect=0.0.0.0:9229

# اگر نیاز واقعی است: increase limit + adjust HPA

# RUNBOOK: Pod NotStarting

## 1. Triage
kubectl get pod <name> -n <ns> -o wide

## 2. Status-specific actions

### Pending
- [ ] `FailedScheduling` در events؟
  - [ ] resources: `kubectl describe nodes | grep Allocated`
  - [ ] taint: `kubectl describe node <n> | grep Taints`
  - [ ] affinity: `kubectl get pod <n> -o jsonpath='{.spec.affinity}'`

### ImagePullBackOff
- [ ] `docker pull <image>` دستی
- [ ] `imagePullSecret` موجود؟
- [ ] registry credentials در secret درست؟

### CrashLoopBackOff
- [ ] `kubectl logs <pod> --previous`
- [ ] exit code:
  - [ ] 137 → OOMKilled → `kubectl describe | grep -A2 Limits`
  - [ ] 1 → app error
- [ ] probe: `kubectl describe | grep -A5 Liveness`

### CreateContainerConfigError
- [ ] ConfigMap/Secret وجود دارد؟
- [ ] key درست است؟

## 3. Escalate if
- Control plane involved
- Multi-node impact
- Data loss risk

## 4. Post-fix
- [ ] Smoke test
- [ ] Update this runbook

🎯 بخش ۶: Anti-Patterns در Troubleshooting
Anti-Pattern	چرا بد	درست
kubectl delete pod بدون diagnose	root cause گم می‌شود	describe + logs --previous اول
kubectl edit در prod	drift، بدون audit	GitOps / patch با annotation
--force --grace-period=0 اول کار	data corruption	آخرین راه‌حل
restart kubelet کورکورانه	دیسک/CNI مشکل واقعی است	journalctl قبل از restart
kubectl exec ... bash بدون log	دستکاری زنده	read-only commands
فقط metric ببین، log نه	context گم می‌شود	metrics + logs + traces
debug در prod بدون break-glass	audit گم می‌شود	با approval + session recording
kubectl logs بدون --previous	crash loop گم می‌شود	--previous را عادت کن
همه pods را همزمان restart	outage	rolling restart
بدون kubectl get events	اولین منبع truth	همیشه اول events
